What the map shows

Durable Task is called from five classes

PipelineRunner publishes the custom status, StepInvoker calls activities and sub-orchestrations, PollingRunner creates timers and reads the clock, RunLeaseGuard acquires and releases the run lease, and RunLeaseKeeper renews it on a durable timer while each stage runs. ActivityOrchestrator only reads the input and creates the replay-safe logger.

Four arrows point back up by design

StepHandle → StepInvoker is the one-line hook that supplies a step's result type, and StepHandle → PollingDefinition is a polling handle carrying its configuration. PollingValidator and PollingRunner → Steps read the public limits MaxPollingChecks and MaxPollingIntervalSeconds.

Definitions reach into Execution twice

IPipelineStage takes a PipelineRuntime, and PollingDefinition holds a PollingSchedule, both of which live in Internal/Execution. Moving those two records into Internal/Definitions would make every arrow between the internal folders point one way. Not changed yet.

The repository is reached only from activities

No orchestration-side class references RunLeaseService or IOrchestrationRunRepository. RunLeaseGuard and RunLeaseKeeper send RunLeaseRequest and RunLeaseRelease to activities, and only the app's OrchestrationRunActivities calls the service, because orchestration code replays and must not do I/O.
